# PhoenixScout 技术方案

版本：2026-10-17 初稿｜对应规则：`docs/规则说明_V2.3.md`

## 1. 总体架构

计算交给代码，判断交给 Claude，A 级由代码把关。

```
① 数据计算层  Java 21 + Spring Boot + SQLite（用户 PC，与 TrendPilot 同规范）
   快照校验 → 排除规则 → 行情 → 基准 → 路径 A 定量 → DefiLlama 收入 → 供应/FDV → 数据质量
   输出 candidates-<日期>.json
② 研究层      Claude 定时任务（每天 10:20 越南时间，连接本机读写 data 目录，见 docs/研究层说明.md）
   对候选做网页检索：回购、销毁、解锁、审计、安全事件、催化剂
   输出 research-<日期>.json，每条结论必须带 url + 日期
③ 评级与报告  Java
   A 级 9 项硬性条件逐条由代码校验；任何一项缺证据 → 上限 B 级
   输出 data/reports/<日期>.md；新 A 级币当天推送（币、理由逐条附来源、风险、估值情景），降级/淘汰推送原因
```

关键约束：LLM 不能直接给 A 级。第十四条的 9 项是代码里的 checklist，每项要么有数据字段，要么有「来源 url + 日期」，否则评级上限为 B（落实第二十一条第 5 款）。

## 2. 数据源（只用免费接口）

| 用途 | 接口 | 每日调用 |
|---|---|---|
| 全宇宙行情：价格、市值、FDV、流通/总量/最大供应 | CoinGecko `/coins/markets`，250/页 × 10 页 | ≈10 |
| 排除名单 | CoinGecko `/coins/markets?category=…`（stablecoins、wrapped-tokens、bridged-tokens、liquid-staking-tokens、liquid-restaking-tokens、exchange-based-tokens、tokenized-gold），每周刷新 | ≈1 |
| 精确 UTC 日线：候选、基准成分、持仓 | CoinGecko `/coins/{id}/market_chart?days=N&interval=daily` 增量补齐 | 100–150 |
| 手续费与收入 | DefiLlama `/overview/fees`（1 次拿全部协议），用 `/protocols` 的 `gecko_id` 映射 | 2–3 |

- 免费公共接口实测限速较紧（约 5 次/分钟会触发 429），统一限流器 + 遵守 Retry-After，SQLite 缓存。
- `/coins/markets` 是实时价，只能标注为「UTC 00:05 快照价（近似）」，仅用于基准 B 与市场广度。
- 路径 A、基准 A 一律使用 market_chart 的 00:00 UTC 点，逐条校验时间戳。
- **价格口径**：CoinGecko 日线 00:00 UTC 点 = 前一 UTC 日收盘价。报告中「日期 D 的价格」均指 D 日 00:00 UTC 点。

## 3. 存储

- `data/raw/<日期>/*.json.gz`：接口原始返回（含请求 URL、请求时间、HTTP 状态）
- SQLite `data/phoenixscout.db`：
  - `price_daily`（币、日期、价格、市值、成交量、来源、请求时间、原始时间戳、标记）——缺失存缺失，绝不填零
  - `snapshot_meta`（版本、SHA-256、创建原因）
  - `fundamentals`（协议、季度、手续费、收入、来源）
  - `supply_events`（解锁/增发/销毁，来源 url + 日期）
  - `research_evidence`（结论、url、日期、核实状态）
  - `candidate_state`、`rating_history`（跟踪状态：新发现/持续 A 级/降级/淘汰）
  - `notifications`（已推送消息，防重复推送）
  - `data_quality_daily`（第二十条各项指标）
- 快照：`data/snapshot/snapshot_vN.json` + `.sha256`；启动先校验，不符则停止依赖快照的计算并告警，绝不重建覆盖。

## 4. 分阶段

| 阶段 | 时间 | 内容 |
|---|---|---|
| P0 | 现在 – 10/30 | 快照归档（服务内置，后台可续跑；Python 脚本为备用）：当前前 2,500 名 × 完整 365 天日线；全部完成后生成只读 snapshot_v1、SHA-256、覆盖率报告并推送 |
| P1 | 约 1 周 | Java 服务骨架；每日行情、排除规则、基准 A/B、路径 A 定量（固定区间与滚动窗口分开）、数据质量、Telegram |
| P2 | 约 1–2 周 | DefiLlama 路径 B、路径 C 与新币观察池、供应模型、估值计算器（第十八条）、claude -p 研究层、A 级 checklist |
| P3 | 之后 | 周/季复核流程；样本外记录与验证（第二十五、二十六条），与同期随机基准对比 |

## 5. P0 相对规则原文的两处扩展（待用户确认写入规则）

1. 初始名单从「前 1,000」扩大到「前 2,500」：降低跌出前 1,000 的严重超跌币被漏掉的概率（第三方审核第 1 条同样指出）。
2. 每个币一次拿完整 365 天，而不是只取两个日期：成本相同，且支撑滚动窗口、基准 A 全程走势和后续验证；本地保存后不再受 365 天窗口限制。

## 6. 已知风险

- 免费数据源对解锁表覆盖差，第十四条第 2 项会是 A 级最常卡住的一项；初期「今日无 A 级」是常态。
- DefiLlama 只覆盖 DeFi 协议，路径 B 天然偏向 DeFi，报告必须写明。
- 已退市/归零/改名的币无法从当前接口获取，快照存在残余幸存者偏差。
